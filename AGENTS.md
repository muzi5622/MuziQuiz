# AGENTS.md — MuziQuiz

## Document authority
Read `MVP.md` for product scope, this `AGENTS.md` for implementation rules, and `PHASES.md` for phase-specific prompts. If they conflict, stop and report the conflict instead of making an undocumented assumption. Keep all three aligned.

## Mission
Build **MuziQuiz**, an original, LAN-only, offline-first audience quiz application inspired by the *interaction pattern* of Mentimeter, not its proprietary code, artwork, branding, or exact UI. A Windows laptop runs one Node.js process serving an optimized participant website, host control dashboard, projector view, API, and Socket.IO. Participants on the same LAN connect through a browser using the laptop's LAN IP and port. Internet access must not be required during events.

## Product priorities
1. Reliability, accurate speed-based scoring, and transparent competition rules over visual animation.
2. Uncomplicated setup for a solo event organizer.
3. Mobile-first participant screen, projector-friendly presentation screen.
4. Support **up to 200 simultaneous connected participants as a tested performance goal**, not an unverified guarantee. A dedicated Wi-Fi LAN/AP setup is required for larger events; never claim Windows Mobile Hotspot handles 200 devices.
5. One active quiz session at a time for MVP; multiple saved quizzes are allowed.
6. No participant registration, online account, cloud dependencies, analytics, or telemetry.

## Technology decisions
- Monorepo with TypeScript throughout.
- `client/`: Vite + React + TypeScript, React Router, plain CSS or Tailwind with entirely local compiled assets.
- `server/`: Node.js + Fastify + Socket.IO + SQLite (`better-sqlite3`) with schema migrations.
- `shared/`: Zod schemas and shared type definitions used by client and server.
- Vitest for unit/integration tests, Playwright for e2e when practical, `socket.io-client` scripted load testing.
- npm workspaces. Prefer few dependencies and readable code. Do not introduce Redis, Kafka, Docker, microservices, cloud DB, authentication providers, or unnecessary abstractions.
- Server serves the production-built Vite site from the same origin and same port as API and WebSocket. Do not require Vite dev server in an event deployment.
- SQLite WAL, sensible indexes and transactions. Avoid synchronous expensive per-response broadcast loops and avoid frequent durable writes on every timer tick.

## Architecture / boundaries
- Server is authoritative over session status, current question, start/end timestamps, submitted answers, scores, and leaderboard.
- Client timers are visual only, computed against server timestamps plus clock offset; submission time and deadline eligibility are judged by server receive time.
- Use `Date.now()` timestamps stored in UTC milliseconds; compare against the server's clock. Do not trust client-provided time or scores.
- Participant reconnect token is generated by server, stored in that browser's localStorage, and treated as a bearer secret. Only its hash is stored server-side; keep token out of URLs. Restore participant identity, score, and current question after reconnect. Do not show another player's private answers.
- Single submission per question per participant, enforced by a UNIQUE constraint `(session_id, question_id, participant_id)`. Retries receive the existing submission's result (idempotent behavior).
- Enforce input validation, string length limits, basic rate limits for join/submit, safe rendering of nicknames and user text, and host-only access to quiz editing and session controls. No `dangerouslySetInnerHTML` with user-controlled content.
- Use a locally configured host password, store a salted password hash, and establish an HttpOnly SameSite session cookie. Require authorization and origin checks for host HTTP routes and Socket.IO host namespace/events. Never embed an admin secret in frontend bundles.
- Bind HTTP to `0.0.0.0` to be reachable on LAN, but document that the LAN should be trusted and isolated from the public internet. Do not implement UPnP, public tunnels, or router port-forwarding.
- Prevent participant data export from exposing reconnect tokens or host credentials.

## Core entities
- `quizzes`: id, title, description, created_at, updated_at.
- `questions`: id, quiz_id, order_index, type (`quiz_mcq` | `poll_mcq`), text, options_json (2-6), correct_option_id nullable for polls, duration_seconds (10-120), base_points, explanation nullable.
- `sessions`: id, quiz_id, six_digit_pin, state, current_question_index, question_started_at, question_ends_at, created_at, ended_at.
- `participants`: id, session_id, nickname, reconnect_token_hash, joined_at, last_seen_at, removed_at nullable.
- `submissions`: id, session_id, participant_id, question_id, option_id, received_at, response_ms, awarded_points, UNIQUE(session_id,participant_id,question_id).
Store participant's total score as query/aggregate or a transactional cached column; ensure correct consistency and stable tie breaks.

## State machine
`LOBBY -> QUESTION_OPEN -> QUESTION_REVEAL -> LEADERBOARD -> QUESTION_OPEN ... -> FINISHED`.
Host actions: start question, close early, reveal answer, show leaderboard, advance, end session. On backend restart, restore the persisted session and treat expired questions as closed based on server timestamps; never re-open expired deadlines. Protect against duplicate host transitions.

## Speed-based scoring — the only scoring mode
- **Only speed scoring exists.** Do not implement a fixed-point/fair mode, mode selector, or toggle in host settings, participant UI, schema, or API. Every scored multiple-choice question rewards correctness **and** response speed.
- For each correct answer received before the deadline, award `round(basePoints * (0.5 + 0.5 * max(0, 1 - responseMs / durationMs)))`, where `responseMs = clamp(serverReceivedAt - serverQuestionStartedAt, 0, durationMs)` and `durationMs = durationSeconds * 1000`. The default `basePoints` is 1000. Thus a correct answer can earn between 50% and 100% of the configured points; incorrect answers, missing answers, and polls earn **0**.
- Example, 20-second question with 1000 base points: correct at 0 seconds = 1000; at 5 seconds = 875; at 10 seconds = 750; at 15 seconds = 625; at 20 seconds = 500 **only if the submission arrived by the deadline**. Enforce the end timestamp exactly: `receivedAt > questionEndsAt` is late and rejected; submissions arriving exactly at the deadline may be accepted.
- Calculate response time **only on the server**, never from a client-supplied timestamp. Record the receive timestamp immediately upon receiving the submission, prior to asynchronous processing, and use the same clock source for question start and receipt. The frontend displays the countdown but does not award points.
- Publish speed-based rules to the host and participants before the game. Local wireless latency can affect scores; measure LAN load and avoid claiming this scoring is perfectly fair under network congestion.
- Sort scores descending, then number of correct answers descending, then lower cumulative valid server response time (`response_ms`) on scored questions; polls do not affect tie breaks. Exact ties share visible competition rank, with stable joined-at/id ordering within a tie.
- Question options must not contain the correct-answer indicator in participant payloads until reveal.
- Mark a participant as answered without broadcasting their answer contents.
- Record network disconnects as separate from wrong answers. Offer a host-controlled re-run/void question option only in a later phase, rather than silently altering rules.

## Routes and views
- `/join`: enter PIN and nickname (if session not already joined).
- `/s/:pin`: participant lobby, answer interface, waiting/reveal, personal rank.
- `/host/login`: host sign-in.
- `/host`: quiz library and management.
- `/host/quizzes/:id`: quiz builder.
- `/host/session/:id`: compatibility redirect to the session projector page.
- `/present/:pin`: projector with host controls for the signed-in host; read-only QR, questions and results for other viewers.
- `/health`: health and version; do not leak secrets.
Use generated QR codes with a reachable LAN URL. If multiple network interfaces exist, allow the host to select an address. Default to numeric IP; optional custom `.local` hostname is outside MVP.

## MVP functional acceptance criteria
1. Running the installed app + local server with WAN unplugged still allows clients on LAN to load, join, answer, and view results.
2. Host can create/edit/delete a quiz with MCQs, choose the correct answer, question duration and maximum points, and persist everything across restart.
3. Host can start one live session, project QR + IP URL + PIN, and manage question transitions.
4. At least 3 real mobile devices can join through Wi-Fi with no accounts and see updates within reasonable LAN latency.
5. No duplicate valid answer accepted; late submissions rejected; correct answer never sent early; speed-based points are computed server-side with deterministic tests at 0%, 25%, 50%, 75% and 100% of the question duration.
6. Reconnecting/reloading restores identity, question state, and score.
7. Live participant count, results, top-10 leaderboard, personal rank, and final podium work.
8. Results export CSV escapes cells correctly to mitigate spreadsheet formula injection; quiz JSON import validates schema and limits size.
9. Host password gates privileged operations, including socket events. Participants can't invoke host controls.
10. 200 concurrent *simulated* Socket.IO clients can join and answer a timed question without crashes, incorrect scores, or loss of accepted submissions in a documented local load test. Report p50/p95 acknowledgment latency and any failures. Simulation alone does not certify 200 physical Wi-Fi devices.

## Phased implementation — stop after each phase and report
### Phase 1: Skeleton and offline LAN serving
Create monorepo, shared schema, Fastify health endpoint, socket connection, SQLite bootstrap, Vite React shell. Production build must be served on one port with `0.0.0.0`; README includes Windows firewall setup and network prerequisites. Add LAN connectivity smoke test.
### Phase 2: Quiz authoring
Build host login, quiz list/editor, MCQ configuration, validation, persistence, JSON import/export. Unit tests for validation.
### Phase 3: Live session/lobby
Session creation, six-digit PIN, locally generated QR, join flow, unique validated nicknames per session, presence, host controls, projector landing screen. Nickname input accepts letters/numbers only (no spaces/symbols), enforced on client and server; normalize compatible Unicode and append a numeric suffix for duplicates. Tests for unauthorized host events and join abuse.
### Phase 4: Real-time quiz/scoring
State machine, question delivery without correct-answer leak, timers, immutable accepted submissions, results, reveal, speed-based scoring only, reconnect; tests for deadlines and duplicate answers.
### Phase 5: Leaderboard/polls/export
Top 10, personal ranks, podium, non-scored MCQ poll and chart, CSV results and statistics. Assign persistent server-selected emoji/color avatars and show participant names/icons arriving on the original projector lobby; names/icons may be public, but private answers remain private.
### Phase 6: Hardening and testing
Simulate 50 then 100 then 200 connected clients; measure latency and memory; reconnect/restart tests; Windows launch scripts; offline audit; responsive polish. Do not claim target achieved until verified.

## Engineering workflow for Codex
- Work on **only one phase per user instruction**. Follow the definitions in `MVP.md` and the relevant gate in `PHASES.md`. Before coding, inspect existing structure and tests, outline files to touch, then implement the smallest working increment.
- At end of every phase run typecheck, lint, unit tests and build; run any available smoke tests. Report commands/results and known limitations.
- Don't silently add new product scope or dependencies. Prefer fixing root causes to workarounds.
- Maintain `README.md` with startup, LAN instructions, IP detection, firewall, offline validation, and data backup instructions.
- Maintain `docs/DECISIONS.md` for trade-offs; keep changes concise.

## Windows operator quickstart (target end state)
- One-time with internet: `npm install` then `npm run build`.
- Event day with no internet: `npm run start` (built server and static client) or included `start-localmenti.cmd`.
- In another terminal: `ipconfig` to find LAN IPv4 (examples only: `192.168.50.10`).
- Participants open `http://<HOST_LAN_IP>:3000` while on same Wi-Fi and enter session PIN; QR code points to this exact URL.
- Windows Defender Firewall allows **inbound TCP 3000 only on the Private network profile**, approved by operator. Never automatically disable firewall globally.
- On Wi-Fi, prevent client/AP isolation, allow local peer communication, ensure LAN DHCP range supports all devices, and avoid captive-portal redirects.

## Not in MVP
Cloud hosting, online accounts, multiple simultaneous sessions, AI question generation, PWA service worker, custom DNS, captive portal, automatic AP provisioning, payment plans, team tournament bracket, SMS, registration email, file uploads, arbitrary HTML, and complex animation libraries.

## Phase 6 interaction refinements (explicit event-host requests)

- A single option tap submits and locks the answer; show the server-measured response time immediately, without awarding points in the answer UI.
- Before every question's answer window, show only the question for a host-configured 3-5 seconds. Withhold options on the server and reject guessed early answers. The answer/scoring start timestamp is the options-release timestamp; the reading period never consumes answer time.
- After answer reveal the host may show the leaderboard or advance directly. Skipping standings keeps unpublished points, totals, ranks and score-history entries sealed in participant payloads. Publishing standings releases all pending revealed rounds; finishing closes/reveals the current answering round and publishes the final totals.
- Persist the last published leaderboard as the animation baseline. Animate score gains and rank movement only after host publication, respect reduced motion, and preserve published state across refresh/restart. No animation library, CDN or timer-driven database writes.

## Authoring refinements and room lifecycle repair

- Import JSON first opens local format instructions with a schema-valid downloadable example and a copyable prompt for an external AI tool. The prompt asks for concise, similarly sized plausible choices, shuffled correct-answer positions, fact checking, then exact version-1 JSON conversion. No in-app AI generation, API connection or cloud dependency is added.
- The MCQ editor exposes automatic saving, explicit Save quiz & return, saved-question counts, question navigation and a clearly marked correct option. All question settings remain part of the saved quiz.
- Deleting a saved quiz also finishes its matching active room, releases the one-active-session slot and preserves session snapshots/immutable submissions/results. The delete confirmation explains this behavior. Deleting another quiz does not affect the active room. The library refreshes active-room state after quiz changes and when the window regains focus.

- JSON import also accepts pasted text in the import guide. Upload and paste share strict version-1 schema and 512 KiB UTF-8 size validation, then use the same host-only import endpoint.

- The library no longer shows the Duplicate quiz action. Recent finished sessions provide expandable saved final top-10 standings and results CSV, using persisted session data even after the original quiz is deleted or the server restarts.

- Quiz screens use large original answer cards and a distinct question-reading stage before options/answer timing. Host/projector and participant reveal charts show per-option counts/percentages and the correct marker only after host reveal. Participants receive a dismissible correctness popup (or neutral unanswered notice); polls have no correctness popup. No points appear before leaderboard publication.

## Quiz-wide answer time (latest host refinement)

The answer time limit is a single quiz.durationSeconds value (integer 10-120, default 20), shared by every MCQ and poll. The editor has one global timing control and no per-question time control. Version-2 quiz JSON requires durationSeconds at quiz level and rejects per-question overrides. Only version-2 JSON is imported; the retired version-1 importer has been removed. Existing saved quizzes migrate with that same policy; existing active/finished session snapshots retain their original durations and deadlines. New sessions snapshot the global value into each runtime question for authoritative scoring. The separate 3-5 second reading period does not consume answer time.

## Explicit save and session navigation

Imported/pasted quizzes are saved immediately. Save quiz & return remains available for a valid already-saved quiz, saves pending edits if needed, and returns to the library only after a successful save. Start session creates a waiting lobby without navigating or starting a question. Open session / Return to lobby opens its host QR/PIN screen. Next: first question starts reading time; options release automatically afterward. Next: close & reveal performs acknowledged close then reveal with the updated revision. Next question advances without publishing scores; Reveal leaderboard remains optional. Database migrations and saved quizzes/results are retained; obsolete build assets and the version-1 importer are removed.

- Host controls use a fresh credentialed WebSocket connection with the browser Origin header; insecure-LAN polling metadata is not relied on. HTTP loads the QR/PIN/control screen independently. Socket failures do not redirect to login unless the HTTP auth endpoint confirms expiry. Genuine sign-in returns to the requested host session using a single post-login redirect. Host cookie and origin authorization remain mandatory.

## Participant focus and host split view

Participant phones show a compact viewport-oriented question/choice screen, a dark high-contrast own-answer popup, and only personal rank/points at publication or finish. Global navigation, room answer charts, other-player standings, score history and repeated help are removed from that screen. Participant socket projections omit option counts, player lists and room leaderboards/podium; correct answer reveal and personal receipts remain. Host/projector retain room charts and animated horizontal-bar standings. The host presentation uses a single full-viewport canvas: questions and published standings replace each other, with controls below. Unpublished new points remain sealed. Layout targets ordinary mobile question lengths; unusually long content remains accessible by overflow rather than clipping choices.

## Unified projector controls

The signed-in host runs the quiz at /present/:pin with QR/PIN lobby, question/result panel, Next/reveal controls and animated leaderboard. The old /host/session/:id UI is removed and that URL redirects to its projector page. Library open-session and finished-session links point to the projector. Unauthenticated projector viewers remain read-only; every host HTTP/socket action still requires the host cookie and origin checks. The live projector omits roster/network management, extra statistics and downloads. After FINISHED, the host sees one CSV download containing all player ranks and points, not only the displayed top ten. Login expiry returns to the projector after sign-in.

## Viewport layout and live waiting lobby

Live participant and host/projector layouts use dynamic viewport sizing and bounded content panels, with questions and published standings shown on the same canvas. Headings use normal letter spacing and readable line heights. Recent finished sessions is collapsed by default and its expanded history list has a bounded height. The waiting lobby shows the local LAN QR/PIN, responsive recent-avatar arrivals with zoom-in animation, and a bottom-right connected-player counter plus joined count. New identities receive a persistent server-randomized unused emoji/color combination, including donut/cat/alien/unicorn/hat variants; existing avatar indices retain their appearance. Motion honors reduced-motion settings and no external join website/assets are required. Stop session is available from the active library banner and host projector; only same-origin authenticated hosts can stop, and final results remain saved.

## Single-canvas presentation and rejoin

The projector uses one full-viewport presentation canvas, without the old green host wrapper or nested light question/ranking cards. Question/answer results and the published leaderboard replace each other on that same canvas, with a compact control bar. The LAN IP/port is prominently displayed in the waiting lobby for manual joining. Typography and participant/PC content receive safe gutters; exceptionally long content stays accessible inside the presentation surface. Existing token holders reconnect directly to the current question with original deadlines, retain accepted points, and receive zero for missed rounds. Entering a saved PIN on the join page offers Resume current question without another nickname. Tokens remain browser/origin scoped and new identities still cannot join mid-quiz.


## Reserved participant identity

MUZI (case-insensitive, including compatible Unicode forms) is reserved across events. Ordinary entries of that name receive a generated Player name. A private join code is the sole exception to the letters/numbers-only join input rule; the server verifies its SHA-256 hash from RESERVED_JOIN_CODE_HASH. The accepted identity displays MUZI with an exclusive skull avatar and gold callout. The code is never a host credential and grants no scoring advantage. Only one reserved identity can join each session; its reconnect token restores it. Ordinary names and avatar/color combinations remain unique within the 200-player limit. Migration renames legacy unverified MUZI entries while retaining IDs, reconnect hashes, answers and points.


## Leaderboard graph and recognition

Host/projector standings hold the prior published points briefly, animate score totals, gains and proportional graph bars together, pause, then move rows into their new rank order. Refresh does not replay an already seen revision, and reduced motion displays final values immediately. The Fastest badge recognizes the lowest average server-measured correct-answer time across all published scored questions; exact ties share it. Polls, wrong answers and pending rounds are excluded. Players with no correct answers cannot receive it. The reserved MUZI identity carries a short Creator badge on the leaderboard with no score or rank advantage. Participant screens continue to show only their own rank and published points.


Leaderboard follow-up: score growth uses a distinct bright graph track and a slower 2600 ms count-up before rank movement. A reveal is remembered only after completion, so interrupted mounting cannot suppress the animation. Replay reveal replays the published score change without publishing new information; reduced-motion settings still apply. Fastest is now a competition-wide correct-answer average, displayed with an avg label, rather than a single-question award.


## Import copying, finished-data reset and presentation motion

The JSON structure disclosure starts collapsed. Copy AI prompt copies only the quiz-writing/conversion prompt; insecure LAN HTTP uses a selected-text copy fallback, with explicit manual-copy feedback if the browser refuses. Host-only Reset finished-session data confirms the action and first backs up SQLite locally, then transactionally removes only FINISHED sessions and their participants, snapshots and submissions. Saved quizzes, credentials and active sessions remain. Migration 10 permits submission deletion only for finished events to support this explicit reset; live answers remain immutable and all answer updates remain blocked. Presentation row spacing inherits its viewport size rather than a fixed 85px override. Full-height colored score graph bars grow with point counting after a short delay, then rows move with native Web Animations (CSS fallback), without external assets. Reduced motion and published-score privacy remain in effect.

The public product name is MuziQuiz. Existing @localmenti workspace scopes, database filenames and browser storage keys are retained for backwards compatibility. Made by MUZI appears on the PIN/nickname join page, QR waiting lobby and final-result footer only; it is absent from live question and intermediate leaderboard screens.
